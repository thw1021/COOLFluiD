# 第 11 章 二次开发指南

本章面向需要扩展 COOLFluiD 的开发者：新边界条件、新通量、新方法乃至全新插件。核心结论先行——**所有可在 CFcase 中按名字引用的对象（方法、命令、物理模型、判据、网格格式……）都是"注册名"，由 Provider 机制在模块装载时登记**；二次开发 ≈ 写一个类 + 一行注册 + 一行 CMake。全部接口与示例以源码实测为准（`src/Common/`、`src/Environment/`、`src/Framework/`、`plugins/FiniteVolume/`、`plugins/Burgers/`）。

---

## 11.1 开发环境与代码规范

### 11.1.1 环境准备

- **工具链**：Linux 下 g++（C++11）+ CMake + make；Windows 见第 8.5 节（VS 工程由 CMake 生成）；
- **开发模式**：建议 `-DCF_ENABLE_SINGLEEXEC=OFF`（默认）的**动态库模式**——改一个插件只需重编该插件（`make <插件名>` 或直接 `make`），增量编译分钟级；静态单可执行模式（第 6.3.2 节）适合交付不适合开发；
- **运行入口**：`./coolfluid-solver --ldir <build>/dso --scase …`——`--ldir` 指向增量编译产物（第 9.5.1 节）；
- **模板起点**：`plugins/EmptySpaceMethod`、`EmptyConvergenceMethod`、`PhysicalModelDummy`、`MarcoTest`（第 5.8.15 节）是最小可编译模板；`AutoTemplateLoader` 提供线代模板装载基准。

### 11.1.2 代码风格约定（实测既有代码）

- 命名空间：`COOLFluiD::Common/Config/Environment/Framework`、`COOLFluiD::Numerics::<插件名>`（物性插件在 `COOLFluiD::Physics::<插件名>`）；
- 命名：类/方法首字母大写（`CellCenterFVM`），成员变量 `m_` 前缀（`m_socketRHS`），宏全大写（`CF_HAVE_*`、`<库名>_API`）；
- 头文件自包含 + include guard：`#ifndef COOLFluiD_<模块>_<文件>_hh`；
- 每个可注册类底部一行 Provider 实例（`.cxx` 末尾），见 11.6.2；
- 新增文件必须登记进插件 `CMakeLists.txt` 的文件清单，否则 `CF_WARN_ORPHAN_FILES` 告警（第 8.2.1 节）。

## 11.2 内核结构总览

### 11.2.1 分层职责

| 层 | 代表目录 | 职责 |
|----|----------|------|
| Common | `src/Common/` | 基础设施：智能指针、容器、日志、异常、PE 封装、字符串/文件工具（约 120 个头文件） |
| Config | `src/Config/` | 配置引擎：`ConfigObject`/`OptionList`/`ConfigArgs`/CFcase 解析（第 9 章） |
| Environment | `src/Environment/` | 运行时：`CFEnv`、`FactoryRegistry`、`ModuleRegister`、`ObjectProvider`、模块装载 |
| Framework | `src/Framework/` | 数值框架：`Method`/`Command`/`PhysicalModel`/`MeshCreator`/`StopCondition`/数据层 |
| plugins | `plugins/<名字>/` | 方法实现：FiniteVolume、FluxReconstruction、NavierStokes 物性等（第 6 章全表） |

### 11.2.2 关键类速查

**Common 层**：`SharedPtr/SelfRegistPtr/SafePtr`（指针）、`DataStorage/DataHandle/DataSocketSource/Sink`（数据）、`CFLog/CFLogger`（日志）、`CFAssert`（断言）、`Exception` 族（~15 个异常类）、`CFMap/CFMap2D/CFMap3D/CFMultiMap/FastMap`（映射）、`Table/Array2D/GrowArray/ConnectivityTable`（容器）、`PE/PEInterface/PEFunctions`（并行）、`LibLoader`（动态库）、`SignalHandler`（信号）、`Event/EventHandler`（事件）、`FactoryBase/ProviderBase`（工厂基类）、`NamedObject/TaggedObject/OwnedObject/SetupObject/NullableObject`（混入基类）。

**Framework 层**：`Method/MethodData`、`NumericalCommand/MethodCommand/CommandGroup`、`NumericalStrategy/MethodStrategy`、`PhysicalModel/PhysicalModelImpl/ConvectionDiffusionPM`、`ConvectiveVarSet/DiffusiveVarSet/BaseTerm`、`MeshCreator/FileReader/FileWriter/FileFormatChecker`、`ConvergenceMethod/ConvergenceMethodData`、`SpaceMethod`、`StopCondition` 族、`DataProcessing`、`OutputFormatter`、`TopologicalRegionSet/TopologicalRegion`、`GeometricEntity/Cell/Face/Edge/Node`、`CFL/ComputeDT`、`SimulationStatus/SubSystem`、`BlockAccumulator`。

### 11.2.3 命名空间、头文件与 API 宏

- 命名空间：`COOLFluiD::Common`、`COOLFluiD::Config`、`COOLFluiD::Environment`、`COOLFluiD::Framework`、`COOLFluiD::Numerics::<插件名>`；
- 头文件自包含：`#include "Framework/X.hh"`、`#include "Common/CFLog.hh"`（插件内 `#include "FiniteVolume/SuperInlet.hh"`）；
- 导出宏：每库一个 `<库名>_API`（如 `Framework_API`、`FiniteVolume_API`），由构建系统按 `CF_BUILD_<库名>_API` 生成（见 11.6.10）。

### 11.2.4 对象生命周期三段式

所有数值对象统一走 `configure → setup → 使用 → unsetup`：

- `configure(ConfigArgs&)`（`ConfigObject`）：从 CFcase 读键，创建命令/策略实例并配置；
- `setup()`（`SetupObject`）：分配数据、构造几何、注册 socket；
- `unsetup()`：逆序释放。

`Method` 的析构会**自动调用 unsetup**（实测 `Method.hh` 注释），命令/策略由 Provider 的 `freeInstance` 释放。

## 11.3 新增物理模型（教程）

新增物理 = 新增 `PhysicalModelType` 注册名 + 配套变量集（`ConvectiveVarSet/DiffusiveVarSet`）与转换器（`VarSetTransformer`）。最小完整范例是 **`Burgers` 插件**（12 个源文件，`plugins/Burgers/`，其 FVM 算例 `burgersFVM.CFcase` 见 7.2.1）。

### 11.3.1 五个步骤

1. **物理模型类**：继承 `Framework::PhysicalModelImpl`，提供维度/方程数/子模型；`.cxx` 底部注册。注意物理模型类**按维度做模板**，且注册名（CFcase `PhysicalModelType`）与变量名无关：

   ```cpp
   // 实测 plugins/Burgers/BurgersPhysicalModel.cxx:25-30
   Environment::ObjectProvider<BurgersPhysicalModel<DIM_2D>,
              PhysicalModelImpl,
              BurgersModule,
              1>
   burgers2DProvider("Burgers2D");
   ```

   ⚠️ 旧版示例写作 `ObjectProvider<BurgersPhysicalModel, …> ("BurgersPhysicalModel")`，**两处均与实测不符**：① 少了维度模板实参 `<DIM_2D>`；② **注册名是 `"Burgers2D"`，不是 `"BurgersPhysicalModel"`**——CFcase 里应写 `PhysicalModelType = Burgers2D`（`plugins/Burgers/testcases/burgersFVM.CFcase` 实测），写 `BurgersPhysicalModel` 会报 Provider not found。
2. **对流变量集**：继承 `ConvectiveVarSet`，实现 `computeFlux/computeJacobian/computePhysicalData` 与特征谱半径；注册 `ConvectiveVarSet` 工厂（实测 `Burgers2DCons` 等）；
3. **源项/粘性项（按需）**：继承 `SourceVarSet`/`DiffusiveVarSet`；
4. **变量集转换器**：写 `XxxToYyy`（继承 `VarSetTransformer`/`VarSetMatrixTransformer`）——`Data.UpdateVar/LinearVar/SolutionVar` 三个变量集之间的一切组合都要有转换器（实测 NavierStokes 的 `Euler2DConsToPuvt` 等成对出现）；
5. **方法侧装配**：FVM 求解需在方法插件侧有对应扩展（Burgers 直接复用 `FiniteVolume` 通用件 + `libBurgers` 物性——`burgersFVM.CFcase` 的 `Modules.Libs` 实测含 `libBurgers`）。

### 11.3.2 检查清单

- 模型注册名、变量集注册名与 CFcase 引用逐字一致（注册名大小写敏感）；
- 转换器组合齐全（缺转换器报 `VarSetTransformer not found`）；
- `nbEqs` 与变量集方程数一致（不一致在 setup 阶段报错）；
- 无化学/热力学数据时用 `PhysicalModelDummy` 起步（第 5.8.15 节）。

> 物性插件（`NavierStokes`、`NEQ`、`MHD`…）的完整模式见第 5.8.2–5.8.6 节；方法插件引用物性只经抽象接口（`ConvectiveVarSet` 等），不跨层直接依赖（11.5.4）。

## 11.4 新增边界条件（教程）

### 11.4.1 基类接口（实测 `NumericalCommand.hh` / `MethodCommand.hh`）

```cpp
class Framework_API NumericalCommand : public Common::OwnedObject,
                                       public Common::SetupObject,
                                       public Config::ConfigObject,
                                       public Common::NonCopyable<NumericalCommand> {
  typedef Environment::ConcreteProvider<NumericalCommand> PROVIDER;
public:
  static void defineConfigOptions(Config::OptionList& options);  // 静态！声明命令键
  virtual void setup();          // 分配命令私有数据
  virtual void unsetup();        // 释放
  virtual void execute();        // 核心：执行逻辑（按需重写）
  void setTrsList(const std::vector<Common::SafePtr<TopologicalRegionSet> >&); // 注入 TRS 列表
  void setCommandGroup(Common::SafePtr<CommandGroup>);   // 组归属（InitComds/BCComds 组）
  void configureNestedSockets(Config::ConfigArgs& args); // 嵌套 socket 配置
};
```

> ⚠️ **`usesTRS()` 不在 `NumericalCommand` 中**：它定义于模板 `MethodCommand<DATA>`（`src/Framework/MethodCommand.hh:94`），且**默认返回 `false`**——旧版写"默认 true：需要 applyTRS"有误。BC 类命令若需要 `applyTRS`，必须自行重写 `virtual bool usesTRS() const { return true; }`，否则方法不会给它注入 TRS 列表。

`MethodCommand<DATA>` 追加共享数据访问：`DATA& getMethodData()`、`void setMethodData(const Common::SharedPtr<DATA>&)`、`static std::string getClassName() { return DATA::getClassName() + "Command"; }`（`MethodCommand.hh:52-62` 实测）。

### 11.4.2 最小命令骨架（以 FVM BC 命令为例）

```cpp
// MyBC.hh
#include "Framework/MethodCommand.hh"
#include "FiniteVolume/CellCenterFVMData.hh"   // 方法共享数据
namespace COOLFluiD { namespace Numerics { namespace FiniteVolume {
class FiniteVolume_API MyBC : public Framework::MethodCommand<CellCenterFVMData> {
public:
  MyBC(const std::string& name);
  static void defineConfigOptions(Config::OptionList& options);  // addConfigOption<…>
  virtual void setup();          // 注意：本项目为 C++98/03 风格，源码不用 override
  virtual void execute();        // 在这里写 BC 赋值逻辑
  virtual bool usesTRS() const { return true; }   // 需要 applyTRS 时必须重写（默认 false）
private:
  Framework::DataSocketSink<CFreal> m_socketRHS;  // 数据槽（getSocket 绑定）
  CFreal m_param;                                // 来自 CFcase 的键
};
}}}
// MyBC.cxx
MethodCommandProvider<MyBC, CellCenterFVMData, FiniteVolumeModule> myBCProvider("MyBC");
```

> ⚠️ **C++98 风格提示**：本项目源码**不使用 `override` 关键字**（全库 0 处），返回类型含模板时写作 `> >`（带空格）。旧版教程骨架中的 `void setup() override;` 在项目原始 C++98 编译标准下无法通过；即便按第 8.3.5 节迁移到 C++17 能编译，也请保持与既有代码风格一致，便于对照。

CFcase 中挂接（第 9.3.9 节模式）：

```
Simulator.SubSystem.CellCenterFVM.BcComds  = MyBC
Simulator.SubSystem.CellCenterFVM.BcNames  = Wall
Simulator.SubSystem.CellCenterFVM.Wall.applyTRS = WallTRS
Simulator.SubSystem.CellCenterFVM.Wall.m_param  = 0.25
```

> 命名空间/名字即身份：注册名 `MyBC` 与类名、文件名约定一致；命令的键注册在 `defineConfigOptions`（静态），实例化时自动带前缀 `CellCenterFVM.Wall.`。

### 11.4.3 命令-数据约定

- **TRS**：`usesTRS()` 重写为 `true` 的命令由方法按 `applyTRS` 注入 `setTrsList`（**`MethodCommand` 默认 `false`**，不重写则不注入），execute 中 `getTrsNames()` 过滤；面/单元几何经 `FaceTrsGeoBuilder`/`CellTrsGeoBuilder` 装配（`Framework/` 实测）；
- **数据**：跨命令/方法数据一律走 `DataSocketSource/Sink`（`getSocket<…>("RHS")`），命令持有 Sink 声明依赖，方法在 setup 期统一分配；
- **Null 命令**：`NullMethodCommand<DATA>`（实测）作为空实现占位，`isNull()/usesTRS()=false`。

### 11.4.4 完整示例：新边界条件工作流

1. **找模板**：在 `plugins/FiniteVolume/` 选最接近的现有命令（如 `SuperInlet`），复制为 `MyBC.hh/.cxx`；
2. **改实现**：替换 `execute()` 逻辑（`getMethodData()` 取物理/几何，socket 读状态、写 `RHS`/`GhostStates`）；键加在 `defineConfigOptions`（`addConfigOption<CFreal>("m_param", …)`）；
3. **注册**：`.cxx` 底部加 `MethodCommandProvider<MyBC, CellCenterFVMData, FiniteVolumeModule> myBCProvider("MyBC");`（11.4.2）；
4. **挂进构建**：`CMakeLists.txt` 的 `MyPlugin_files` 追加两文件（11.6.6）；重新 `cmake` + `make`（增量仅数分钟）；
5. **算例验证**：仿第 9.5 节流程，`BcComds/BcNames/applyTRS` 挂上新命令，`--testEnv` 先行；
6. **固化**：`### Residual` 标定 + `--residual/--tolerance` 回归（第 9.5.1 节）。

## 11.5 新增空间方法（教程）

### 11.5.1 基类接口（实测 `Method.hh`）

```cpp
class Framework_API Method : public Common::OwnedObject, public Common::SetupObject,
                             public Config::ConfigObject, public Common::SignalHandler,
                             public Common::NonCopyable<Method> {
public:
  virtual void configure(Config::ConfigArgs& args);                       // 创建/配置命令组
  virtual std::vector< Common::SafePtr<NumericalCommand> > getCommandList() const;      // 实测 Method.hh:86（注意 C++98 的 "> >"）
  virtual std::vector<Common::SafePtr<Framework::NumericalStrategy> > getStrategyList() const;  // :93
  virtual Common::SafePtr<Framework::MethodData> getMethodData() const = 0;
  virtual void run_function(const std::string& func) = 0;                 // "setup"/"process"/…
  virtual void setMethodImpl() = 0;      // 真 setup（配置后调用）
  virtual void unsetMethodImpl() = 0;    // 真 unsetup
  virtual void registActionListeners();  // 事件监听注册
  virtual void setNonRootMethods();      // 协作方法（并行）设为非根
};
```

### 11.5.2 方法三阶段与信号分发

方法经 `SignalHandler` 处理 `methodSignal`（`"setup"`、`"unsetup"`、`"process"`、`"run"` 等，第 2 章）：`configure → setMethodImpl → process/run → unsetMethodImpl`；命令通过 `CommandGroup` 分发（组 = CFcase 中的 `InitComds/SetupCom/BcComds/…`）。

### 11.5.3 最小方法骨架（以 CellCenterFVM 为参照）

| 组成 | 要求 |
|------|------|
| `MyMethod` | 继承 `SpaceMethod`（或 `ConvergenceMethod` 等），实现四个纯虚 + 定义配置键；命名空间 `Numerics::MyMethod`；头文件 `MyMethod.hh` 带 `MyMethod_API` |
| `MyMethodData` | 继承 `MethodData`，聚合命令共享的指针/配置（如 `FluxSplitter`、`PolyRec` 由 `Data` 创建并持有） |
| `MyMethodModule` | 模块注册类（11.6.4） |
| 注册行 | `Environment::ObjectProvider<MyMethod, SpaceMethod, MyMethodModule, 1> provider("MyMethod");`（NBARGS=1：`create(ConfigArgs)`） |

### 11.5.4 方法命名空间约定

方法实现统一放 `namespace COOLFluiD { namespace Numerics { namespace <插件名> { … } } }`（实测 FiniteVolume/FluxReconstruction 等全部遵循）；物性插件（NavierStokes 等）在 `Physics` 命名空间，方法插件引用物性只经抽象接口（`ConvectiveVarSet` 等），不跨层直接依赖。

## 11.6 插件注册与加载

### 11.6.1 Provider 工作原理

```
模块装载(LibLoader dlopen)
   → 静态对象构造（每个 .cxx 底部的 Provider 实例）
   → ObjectProvider 构造 → 注册到 ModuleRegister 的自注册表
   → FactoryRegistry 聚合所有 Factory<BASE>
运行时：CFcase 给出注册名 → Factory::getProvider(name) → create() → SelfRegistPtr
```

- 每个基类（`SpaceMethod`、`NumericalCommand`…）自带 `typedef ... PROVIDER` 与 `static std::string getClassName()`；
- `Factory<BASE>` 是**单例**，按 `BASE::getClassName()` 索引（非单可执行模式，实测 `Factory.hh`）；
- 注册名**重复时告警并覆盖**（实测 `regist()` 打印 "a provider with the name […] was found" 后覆盖）；`getProvider` 找不到时抛 `Common::NoSuchValueException`。

### 11.6.2 注册模板三件套（实测）

| 模板 | 用途 | 实测实例 |
|------|------|----------|
| `Environment::ObjectProvider<CONCRETE, BASE, MODULE, NBARGS>` | 方法、物理模型、判据等无数据聚合对象 | `ObjectProvider<CellCenterFVM, SpaceMethod, FiniteVolumeModule, 1> cellCenterFVMMethodProvider("CellCenterFVM");`（NBARGS=1 表示 `create(arg)` 带 `ConfigArgs` 参数） |
| `Framework::MethodCommandProvider<COMMAND, DATA, MODULE>` | 方法的命令（共享 DATA） | `MethodCommandProvider<SuperInlet, CellCenterFVMData, FiniteVolumeModule> superInletFVMCCProvider("SuperInletFVMCC");` |
| `Framework::MethodStrategyProvider<STRATEGY, DATA, MODULE>` | 方法策略（重构器、通量等） | 各 `*StrategyProvider` 实例（如 FVM 的 PolyRec） |

另有专用 Provider：`BaseGeometricEntityProvider`（几何实体，NBARGS 表示参数个数）、`IntegratorImplProvider`（积分实现）、`BaseMethodCommandProvider`（命令族基类）。注册模板共性：**构造函数内 `ModuleRegister<MODULE>::getInstance().getSelfRegistry().regist(this)` 完成静态自注册**（单可执行模式 `CF_HAVE_SINGLE_EXEC` 下跳过——对象直接编进主程序）。

### 11.6.6 CMakeLists 模板（实测结构）

```cmake
IF ( NOT CF_HAVE_SINGLE_EXEC ) SET ( MYLIBNAME "MyPlugin" )
ELSE () SET ( MYLIBNAME "coolfluid-solver" ) ENDIF()

LIST ( APPEND MyPlugin_files  MyMethod.cxx MyMethod.hh MyCommand.cxx MyCommand.hh )

# 外部头/库：LIST ( APPEND MyPlugin_includedirs ${MPI_INCLUDE_DIR} )；${MyPlugin_libs}
IF ( NOT CF_HAVE_SINGLE_EXEC )
  CF_ADD_PLUGIN_LIBRARY ( MyPlugin )
ELSE()
  FOREACH ( AFILE ${MyPlugin_files} ) LIST ( APPEND coolfluid-solver_files ../../plugins/MyPlugin/${AFILE} ) ENDFOREACH()
ENDIF()
CF_WARN_ORPHAN_FILES()   # 源码目录里没纳入清单的文件会告警（第 8.2.1 节）
```

### 11.6.7 `CF_ADD_LIBRARY` 宏要点（实测 `cmake/macros/CFAddLibrary.cmake`）

- `CF_BUILD_<库名>`：默认 ON，可关（`MARK_AS_ADVANCED`）；
- `<库名>_kernellib`：置 ON 则计入 `CF_KERNEL_LIBS`（Kernel 库列表，如 Common/Framework）；
- `CF_BUILD_<库名>_API`：是否发布 API（默认 = kernellib，插件默认不发布头文件）；
- `BUILD_SHARED_LIBS` 决定 SHARED/STATIC；`<库名>_requires_mods` 声明依赖模块，缺失自动跳过（`_will_compile OFF`）；
- 源码按 `CF_SEPARATE_SOURCES` 分拣 `.hh/.cxx/.ci/.cu`；`CF_WARN_ORPHAN_FILES` 兜底。

### 11.6.8 装载链路

CFcase `Simulator.Modules.Libs = libMyPlugin` → `LibLoader`（POSIX `dlopen` / Win32 `LoadLibrary`，实测 `PosixDlopenLibLoader/Win32LibLoader`）→ 静态 Provider 自注册 → `FactoryRegistry` 可查。**未列进 `Modules.Libs` 的插件不会注册**——运行时报 `NoSuchValueException`（"In factory of [SpaceMethod] a provider with the name [MyMethod] was not found"）即是漏加载的典型症状。

### 11.6.9 CUDA 分支

插件内可仿照实测写法：`IF (NOT CF_HAVE_CUDA)` 编 `.cxx` 版本，`ELSE()` 编 `.cu` 版本并追加 `${CUDA_INCLUDE_DIR}/${CUDA_LIBRARIES}`（FiniteVolume 的 `LaxFriedFlux` 即此模式，含源码复制 `.cxx→.cu` 的 `EXECUTE_PROCESS`）。

### 11.6.10 插件 API 与导出符号

- **`<库名>_API`**：由构建系统生成（`CF_BUILD_<库名>_API=ON` 时发布头文件到安装 include 目录），Kernel 库默认发布、插件默认不发布（实测宏注释）；
- **头文件自包含**：每个 `.hh` 带 include guard（`#ifndef COOLFluiD_…_hh`）并可独立编译；
- **跨插件依赖**：声明方在 `CMakeLists.txt` 里 `LIST(APPEND 本插件_cflibs 目标插件)`，include 用 `<插件名>/头.hh` 形式；依赖方向自下而上（Framework ← ShapeFunctions ← 方法插件 ← 后处理插件）。

## 11.8 调试与测试

### 11.8.1 运行期诊断

- **库路径**：`--ldir <build>/dso` 指向增量编译产物（第 9.5.1 节）；
- **配置消费检查**：`CFEnv.ErrorOnUnusedConfig=true` 检查 CFcase 键是否被消费（第 9.3.1 节）——新命令未读到的键会在此暴露；
- **Provider 未注册**：先查 `Modules.Libs` 是否含插件名；`--testEnv` 预检装载（第 0.3.7 节）；
- **日志**：`--log=700`（DEBUG_MIN）起看细节，`--log=1000`（DEBUG）含 socket/命令跟踪（第 9.5.1 节）。

### 11.8.2 单元测试与回归

- 内核单元测试位于 `src/UnitTests/`（`utest-*.cxx`），由 `CF_ENABLE_UNITTESTS` 启用（附 B-26；插件中无 `testsuite/` 目录）；
- 算例回归：`ctest` 驱动 `plugins/*/testcases/`（`CF_TESTCASES_NCPUS` 控制并行数，第 8.2.1 节）；
- 结果固化：`### Residual` 头注释标定 + `--residual/--tolerance` 自动比对（第 9.5.1 节）。
